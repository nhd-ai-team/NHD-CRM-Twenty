## 0. 一句话总览

官网表单只提交 **5 个字段**（Name / Phone / Email / Country-Region / Message），CRM 把它们**统一收口进「线索（商机 Opportunity）」**。联系人（客户主数据 Person）**不在表单提交时建立**，而是在销售点「转客户」时，由 CRM 读取线索上的「联系人姓名」自动生成并回填。

```
官网表单 5 字段 ──POST /api/website/form──▶ 线索(opportunity)
                                              │  Name → lianXiRenXingMing（官网联系人姓名·暂存）
                                              │  Phone/Email/Country/Message → 对应线索字段
                                              ▼
                                      （销售点「转客户」）
                                              │  读取 lianXiRenXingMing
                                              ▼
                                      客户主数据 Person（nameFirstName = 官网联系人姓名）
                                              │  回填 opportunity.pointOfContactId（"客户联系人"字段）
                                              ▼
                                      线索 → 客户 → 项目 漏斗
                                              │
                                      （沟通后修正姓名）
                                              │  更新 官网联系人姓名 → 自动反写 → 客户联系人姓名
                                              ▼
                                      客户主数据 Person.nameFirstName 同步更新
```

> **「线索id」统一口径（2026-08-17 v4 落地）**：
> ⚠️ 先纠正一个常见误解——**线索页里你看到的"公司名称"并不是线索id 字段的值**。线上实测：
> - `leadNo`（线索id）存的是编号，如 `XS-20260817185541` / 历史数据 `FK-3A9F2C1B7E`，**永远是线索流水号，从不是公司名**。
> - 你看到的"公司名称"出现在 **线索标题 `name`** 列，其生成规则是 `company || email || phone || '官网表单线索'`——只要该线索带了公司，`name` 就等于公司名（公司名来自 `companyId` 关联，转客户/带公司建线索时写入，与线索id 是**两条独立字段**）。
> - 结论：**线索id ≠ 关联公司表单的公司名称**，二者无关；需要追溯"这个客户/项目来自哪条线索"，看的就是线索id。
> - **三对象统一标签「线索id」**：`leadNo` 在 **线索 / 客户 / 项目** 三个对象上都注册了同名字段，v4 起三者**标签统一为「线索id」**（原先曾分别叫线索访客ID/客户访客ID/项目访客ID，v4 撤销该区分，改回统一名，便于用户跨对象识别同源）。物理字段名仍是 `leadNo`。
> - **生成规则改为可读时间戳（v4）**：原先 `FK-` + 10 位随机十六进制（`index.js:1424`），v4 改为 `XS-YYYYMMDDHHMMSS`（`generateLeadId()`），如 `XS-20260817185541`，用户一眼能看出线索创建时间，且同一秒内极端并发会自动追加 2 位随机后缀防重。历史 `FK-` 数据保留不变。
> - **转客户 / 转项目时线索id 同源同步（v3 已实现，v4 继续生效）**：
>   - `convert-to-person`：把线索的 `leadNo` 写入关联客户(person)的 `leadNo`（UPDATE 用 `COALESCE` 不覆盖已有值，INSERT 直接写入）。
>   - `convert-to-project`（`upsertProjectFromOpportunity`）：把线索的 `leadNo` 写入项目 `_xiangMu.leadNo`（INSERT 直接写入、UPDATE 用 `COALESCE` 兜底）。
>   - 效果：在客户详情、项目详情看到的「线索id」就是它来源线索的编号，**客户/项目 → 线索 全程可追溯**。
> - **线索列表默认列位置（v3 已设）**：线索默认 TABLE 视图已将「线索id」设为**可见且位于第 2 列**（紧随记录名首列之后）。Twenty 列表首列固定为记录名（不可排到其前），故"线索id"最前只能第 2 列，前端限制而非缺陷。

## 4. 联系人收口规则（重点纠正）

**关键纠正**：表单的 `Name` **不再**在提交时直接建一条客户联系人（Person）记录。正确链路是：

1. **表单提交时**：`Name` 仅写入线索的 `opportunity.lianXiRenXingMing`（CRM 界面标签：**官网联系人姓名**文本列），**不建 Person、不写 `pointOfContactId`**。
2. **销售点「转客户」时**：`upsertPersonFromOpportunity` 读取 `lianXiRenXingMing`（回退到线索标题）作为客户主数据 Person 的 `nameFirstName`，生成/更新 Person，并自动回填 `opportunity.pointOfContactId` 与 `linkedPersonId`（即 CRM 线索详情页**「客户联系人」**字段显示该姓名）。
3. 同一线索重复点「转客户」**不会**建重复 Person（按 `syncGroupCode` 去重，返回已存在记录）。

> 对话工作台「转线索」入口（convert-to-lead）也已统一为相同口径：联系人姓名只写 `lianXiRenXingMing`，不立即建 Person。两条入口行为一致，无冲突。

### 4.1 姓名反写规则（问题 2 落地 · 2026-08-17 新增）

沟通后发现表单姓名有误、在 CRM 修改**「官网联系人姓名」**时，系统会**自动把新姓名同步写回到关联的「客户联系人」**（Person 的 `nameFirstName`），保证两处姓名一致。

- **触发条件**：线索已转客户（即已关联 Person、`pointOfContactId` 非空），且「官网联系人姓名」**确实被修改为非空值**。
- **实现**：数据库触发器 `opportunity_website_contact_name_sync_after_update`（函数 `conv.sync_website_contact_name_to_person()`，AFTER UPDATE on opportunity）。
- **防误伤**：仅当姓名**变化**时才反写；修改其他无关字段（如留言、国家）**不会**覆盖客户联系人姓名；清空官网联系人姓名也**不会**清空客户联系人姓名。
- **不污染"未转客户"状态**：该触发器只写 Person 姓名，不动 `pointOfContactId`，因此不会让线索误判为"已转客户"。

## 5. 公司处理规则

- 表单**带公司名**（`company` 字段）→ 用 `findCompanyByExactName`（按名模糊匹配去重）查找已有公司，没有则新建，并写 `opportunity.companyId` + `person.companyId`，所有公司统一收口进「公司表」（前端锁定，用户不手动管理）。
- 表单**不带公司名**（当前 5 字段表单即如此）→ **不建公司**，`companyId` 为空。
- 公司表参与「线索 → 客户 → 项目」漏斗的统一数据分配。

## 6. 重要业务约束：转客户需先填「客户需求产品」

**转客户（`convert-to-person`）与转项目（`convert-to-project`）都硬性要求线索的 `keHuXuQiuChanPin`（客户需求产品）非空**，否则返回 400：

```json
{ "error": "客户需求产品未填写", "detail": "请先在线索表填写「客户需求产品」，再执行转客户。" }
```

**对官网表单的影响**：当前 5 字段表单**不含 product 字段**，因此线索进来后，销售必须**先在线索详情手动填写「客户需求产品」**，才能点「转客户 / 转项目」完成漏斗。

> 可选增强（待确认）：若希望表单提交即满足转客户条件，可在官网表单增加「需求产品」字段并映射为 `product`（后端已支持，见 §3）。当前未做，故列为约束而非缺陷。

## 7. 幂等 / 去重（代码级验证结论）

- **已转过客户的线索再次转客户**：返回已存在的 Person（`created:false`），不产生重复客户。
- **已转过项目的线索再次转项目**：返回已存在的项目（`created:false`），不产生重复项目。
- 去重键：客户按 `syncGroupCode`、项目按 `sourceOpportunityId`（=线索 id）。
- 结论：销售可放心多次点击「转客户/转项目」，漏斗里同一线索永远只挂 1 个客户、1 个项目，无脏数据。

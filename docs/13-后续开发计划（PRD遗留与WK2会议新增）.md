## 二、本次会议新增 / 需要澄清的点（PRD 里没有，或者跟原设计冲突）

### 全新需求

| 点 | 说明 | 状态 |
|---|---|---|
| **官网 widget.js 支持访客发附件** | PRD 原文是"附件发送优先支持 WhatsApp"，官网访客端从没规划过发附件；widget.js 源码里**完全没有文件选择控件**，是从零做 | 需求明确，待排期。**关键前提**：做完要出新版本号，还需要协调官网供应商更新嵌入代码里的 `<script src>` 版本号，这一步没法单方面推送生效 |
| **跟进模块支持上传附件** | 会议上客户方提出，咸海东当场回应"我的理解可能有点偏差，我再去看一下" | **需求边界没对齐**，不能直接排期，得先跟对方确认清楚：是要能上传文件当跟进证据，还是别的意思 |

| 点 | PRD/原设计 | 会议上的分歧 |
|---|---|---|
| **WhatsApp 主动新建会话方式** | 设计结论是"必须先有对方号码、发一条消息，才能把对话拉进 CRM"（技术调研结果） | 客户方对比了另一个工具（"徐曼云"提到的），对方是直接搜号码就能建，双方没达成一致，**这是接下来要重点澄清的分歧点**，不是简单的 bug |

## 三、跟已在推进的方向对应关系

有两项会议内容其实和已经在做的事是同一件事，不算新增，应该合并规划，不要重复设计：

1. **"跟进目前只关联到 Opportunity，还没关联到 Project 和 People"** ←→ 正在做的 **Opp/People/Project 三方数据整合**（1.0 已定案走强标识符精确匹配）。跟进记录的关联范围应该跟这套三方关联逻辑保持一致，不要单独再搭一套。
2. **"重复建档"去重** ←→ **官网域名归纳 + syncGroupCode** 机制，PRD 里"客户跨平台身份合并"那条本质是同一个功能，只是会议里说的是"待众测"的阶段。

## 四、建议的排期思路

不是最终优先级决定，只是从依赖关系角度给的建议：

- **P0（阻塞类）**：附件收发闭环（WhatsApp 那边在修，官网 widget 这块要单独排）——本周唯一没完成又被反复提到的功能
- **P1（需要先澄清才能排期）**：跟进模块附件需求、WhatsApp 建会话方式分歧——这两个不澄清清楚，做了也可能返工
- **P2（新功能，边界清楚可直接排）**：官网 widget 支持访客发附件——虽然工作量不小（还要协调供应商），但需求本身没有歧义
- **P3（待验证，不一定是真问题）**：多语言链路偶发无响应、WhatsApp 掉线、多端登录冲突——先复现/验证，确认是不是真需要修

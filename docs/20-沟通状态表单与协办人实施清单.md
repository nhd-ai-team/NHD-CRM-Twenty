## 阶段 1 · 沟通状态表单（方案 C）

### 1.1 注册字段（`duiHuaLiShi`）

| 字段名 | 标签 | 类型 | 说明 |
|---|---|---|---|
| `channel` | 渠道 | SELECT | 官网客服/WhatsApp/Instagram/Facebook/邮件 |
| `conversationStatus` | 会话状态 | SELECT | 进行中/AI托管/人工接管/已关闭 |
| `communicationResult` | 沟通结果 | SELECT | 待跟进/已回复/已转化/无效/其他（枚举待定稿） |
| `owner` | 负责人 | RELATION→成员 | 或 TEXT 兜底（见决策点） |
| `lastMessageAt` | 最近消息时间 | DATE_TIME | |
| `lastMessagePreview` | 最新消息摘要 | TEXT | |
| `messageCount` | 消息数 | NUMBER | |
| `hasHumanMessage` | 含人工消息 | BOOLEAN | |
| `conversationId` | 会话外部ID | TEXT | 幂等键，隐藏 |

- `name` 复用为会话标题。
- 注册方式：mint ES256 JWT（kid=`4dafcf64-…`、type=ACCESS、Admin userId）→ POST `/metadata` `createOneField` 逐字段注册；SELECT 需带 `options`，RELATION 需带 `relationTargetObjectMetadataId`。

### 1.2 middleware 同步（新增 `syncConversationToHistory`）

- 幂等键 `conversationId = conv.conversations.id`。
- 在会话创建/更新入口（`persistWhatsAppMessage`、官网客服、官网表单、Instagram、Facebook）调用。
- **只同步新会话**，不回填历史。
- 写 Twenty 用现有 GraphQL client（`createOneDuiHuaLiShi`/`updateOneDuiHuaLiShi`），状态/摘要/消息数/时间随消息增量更新。

### 1.3 导航与钻取（`nginx/inject/src/20-drill.js`）

- 现状：`/objects/duiHuaLiShis` 拦截 → `showView('history')`（气泡查看器）。
- 目标：**表格/看板用原生**；点进单条记录 → 「查看对话内容」按钮 → **内联文本弹窗**（2026-08-19 起）：拉 `GET /conv-api/conversations/:id/messages` 渲染消息文本（客户/实际回复成员姓名/AI 标签+时间+内容+附件链接），顶部关键词过滤即时定位；底部保留「在完整对话页打开」可选入口。不再整页跳转（用户诉求：切页后难以快速定位想看的内容）。对话工作台会话头部另有「查看历史记录」按钮，复用同一右侧面板查询当前会话。
- 按钮显隐：仅当检测到 duiHuaLiShi 详情上下文（整页路由 `/object(s)/duiHuaLiShi[s]/<uuid>` 或右侧抽屉内 duiHuaLiShi 自链接）时注入；离开上下文自动清理（2026-08-19 移除 S3 宽泛兜底后修复残留）。

### 1.4 部署 + 验证

- 字段注册后清 Redis 元数据缓存 + 重启 server/worker/portal；验证列落库。
- middleware `docker cp` + restart；`node --check` 先行。
- chat-nav `jsdom` 回归（699/236）+ 四处 md5 一致。
- 真实渠道走一条新会话，验证 duiHuaLiShis 记录落库、原生表格可见、点进能钻取到气泡。

## 阶段 2 · 线索协办人（方案 B）— 已实现（2026-08-18）

> 代码真相：协作人字段是**单数关系** `xieBanRenId`（opportunity/person/_xiangMu/company 均有），非设计稿设想的多对多；`xieZuoRen2Id` 同为单数协作人字段。主负责人 = `ownerId`。

### 2.1 字段整合

- 不删 `xieZuoRen2Id`；改为**两个协作人字段都生效**：`conversationVisibilityWhere` 的 `linkedCrmAssigneeSql` 已同时纳入 `xieBanRenId` 与 `xieZuoRen2Id`（opportunity/person/_xiangMu），即「收敛」语义以"两个字段均放行"实现，无迁移成本。

### 2.2 middleware 权限（核心）— 已实现

- `lib/conversation-visibility.js` 的 `linkedCrmAssigneeSql` 增 `xieZuoRen2Id`（见 2.1）；归属该记录的会话，协办人可看（history 视图 `allowPrivilegedAllChannels`）、可接管/可回复（sales 协作人非 boss，不受只读限制）。
- 新增通用端点 `GET/PUT /api/crm/:objectType/:id/collaborators`（`objectType`∈opportunity/person/xiangMu），读写 `xieBanRenId`；GET 额外返回 `canEdit`(owner 或 admin/boss) 与 `currentUserId`。
- 新增 `GET /api/crm/members`（任意登录成员可访问）返回 `{workspaceMemberId,name}` 供选择器。
- 授权：**仅主负责人本人(`ownerId`) 或 `admin` 可 PUT**；`boss` 仅有查看权（GET canEdit=false）。

### 2.3 UI 注入 — 已实现

- `nginx/inject/chat-nav.js` 新增「协办人」悬浮按钮（左下 `left:24px`，避开「跟进记录」右下）+ 弹窗：展示当前协办人，owner/admin 见成员下拉+保存/清除；非 owner/admin 仅只读。挂入 `tick()`，`ensureCollaboratorEntry` 检测 `/objects/{opportunities|people|_xiangMus}/<uuid>` 整页路由。
- jsdom 回归 699/236 PASS；四处 md5 一致 `c46c43fe`。

### 2.4 部署 + 验证

- middleware index.js `f2afc257` + lib/conversation-visibility.js `6f6bb535`（docker cp + restart，health 200）；chat-nav.js `c46c43fe`（4-way md5）。
- 路由存活验证：`/conv-api/crm/{members,opportunity|person|xiangMu/.../collaborators}` 无 token 均 401（鉴权生效）。
- **待用户浏览器实测**：以主负责人身份设置协办人 → 用协办人账号确认能看到该记录对话、可接管回复；非主负责人设置应被 403 拒绝。

### 已知缺口 / 待确认（未做）
- **客户(account/company)**：`company.xieBanRenId` 字段存在，但 `linkedCrmAssigneeSql` 未 join company，对话可见性未接入；UI 按钮也仅 opportunity/person/_xiangMu（company 的 URL slug 未确认）。需确认你语境里「客户」= company 还是 person（person 已覆盖）。
- **Twenty 原生记录可见性**：middleware 只管对话可见性；协作人能否在 Twenty UI 打开 opportunity / duiHuaLiShi 记录取决于对象权限配置（sales 对这两对象是否可读 / 隐式共享），需另配或验证。
- **抽屉模式**：协办人按钮同「跟进记录」仅整页 URL 检测，抽屉打开不显示（如需抽屉支持需复用钻取按钮的锚点扫描法）。

## 决策点（实施中拍板）

1. `owner` 字段：RELATION→成员（原生、可筛选，注册较复杂） vs TEXT（简单，失去原生关联）。
2. 「沟通结果」枚举最终值域。
3. 协办人字段是否收敛为一个多对多（删 `xieZuoRen2`）。
4. 会话→历史同步写 Twenty：GraphQL（推荐，复用现有 client） vs 直写 workspace 表（需先确认 targetTableName）。

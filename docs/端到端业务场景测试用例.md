# 端到端业务场景测试用例（按用户实际操作流程）

> 版本：v4 · 2026-08-20
> 目标：按真实用户在 CRM 前端的操作路径验证完整业务链路。接口与数据库断言只作为辅助定位，不替代用户流程验收。

## 0. 代码结构与数据模型速览

### 0.1 系统架构

```
官网表单 / WhatsApp 等渠道
        │
        ▼
Cloudflare 隧道（crm.chinanhd.com）
        │
        ▼
portal nginx（twenty-twenty-portal-1 :3000）
        │
        ├─ /api/*（机会/客户/项目等 Twenty 业务）→ Twenty server（:3000 GraphQL）
        └─ /api/conversations/*、/api/whatsapp/*、/api/website/form、
           /api/opportunities/:id/convert-to-* → middleware（:3002）
        │
        ▼
PostgreSQL（twenty-db-1）+ Redis（元数据/缓存）
```

**关键容器**：`twenty-server-1`(GraphQL 引擎)、`twenty-worker-1`(后台任务)、`twenty-twenty-portal-1`(nginx 门户)、`twenty-middleware-1`(Node/Express 业务中间件)、`twenty-db-1`(Postgres)、`twenty-redis-1`(缓存)。

### 0.2 核心数据模型（三表漏斗 + 会话工作台）

### 0.6 WhatsApp 会话 ID 归一化

WAHA 可能对同一联系人返回两种 chatId：

| 类型 | 示例 | CRM 内部用途 |
|---|---|---|
| 手机号 JID | `8615810780090@c.us` | CRM 标准会话键，写入 `conv.conversations.external_chat_id` |
| LID | `200751838167131@lid` | WAHA provider chatId，仅用于真实发送或兼容查找 |

入站和出站都必须归一到 `<phone>@c.us`。测试时如果发现同一手机号出现两条会话，应判定为 P0 缺陷。

### 0.7 WhatsApp 状态巡检

middleware 启动后会定时执行 WAHA 状态巡检：

| 配置 | 默认值 | 说明 |
|---|---|---|
| `WAHA_STATUS_POLL_SECONDS` | `60` | 巡检间隔，最低 30 秒 |
| `WAHA_AUTO_RESTART_ON_DISCONNECT` | `true` | 对 `FAILED` / `STOPPED` 自动尝试 restart |
| `WAHA_WEBHOOK_URL` | `http://middleware:3002/api/whatsapp/webhook` | session webhook 内网地址 |

状态落点：`conv.channel_accounts.status` 与 `metadata.lastWahaStatus`、`metadata.lastWahaStatusAt`、`metadata.lastWahaStatusSource`。

## 1. 用户实际操作全链路测试（主验收）

本章是端到端测试的主入口。测试人员应优先按本章执行，确认用户在页面上能完成真实业务动作；后面的接口和数据库用例只用于失败定位与补充验证。

### E2E-01 销售首次登录并绑定 WhatsApp

| 项 | 内容 |
|---|---|
| 操作者 | 销售账号 A |
| 入口 | CRM 登录页 → 左侧「设置」→「账户 / 渠道」 |
| 前置 | CRM、middleware、WAHA 服务已启动；销售 A 有可用于测试的 WhatsApp 账号 |

操作步骤：

1. 打开 CRM 登录页，输入销售 A 的邮箱和密码登录。
2. 登录成功后确认左侧主菜单显示：对话工作台、邮箱、线索、客户、项目、沟通状态、设置。
3. 点击左侧「设置」。
4. 在设置页左侧点击「账户」下的「渠道」。
5. 确认右侧页面显示 WhatsApp 绑定卡片，左侧设置菜单不消失。
6. 点击「刷新状态」，查看当前 WhatsApp 状态。
7. 若未绑定，点击「启动/刷新二维码」或使用手机号配对码完成绑定。
8. 绑定成功后点击「绑定到我的账号」。
9. 退出设置页，重新进入「对话工作台」。

预期结果：

- 登录后页面不白屏、不无限刷新。
- 进入渠道页后，左侧设置菜单保持原生样式，右侧只切换为渠道绑定内容。
- WhatsApp 状态显示为可读中文状态；失败时说明原因。
- 绑定成功后显示绑定号码、显示名称、WhatsApp ID、CRM 绑定用户。
- 对话工作台中 WhatsApp 渠道可见，但只显示销售 A 自己绑定账号相关会话。

辅助断言：

- `conv.channel_accounts` 中存在销售 A 的绑定记录。
- 状态为 `WORKING` 时可收发；`SCAN_QR_CODE` 时需要重新扫码/配对。

### E2E-02 WhatsApp 客户发起咨询，销售接管并转线索

| 项 | 内容 |
|---|---|
| 操作者 | 外部 WhatsApp 客户 + 销售账号 A |
| 入口 | 外部 WhatsApp → CRM「对话工作台」 |
| 前置 | 销售 A 已完成 E2E-01，WhatsApp 状态为 `WORKING` |

操作步骤：

1. 外部 WhatsApp 客户向销售 A 绑定的 WhatsApp 号发送一条测试消息。
2. 销售 A 登录 CRM，进入「对话工作台」。
3. 点击顶部「WhatsApp」渠道。
4. 在左侧会话列表中找到刚进入的新会话。
5. 打开该会话，确认中间聊天区能看到客户刚发送的消息。
6. 点击底部「接管会话」。
7. 在确认弹窗中点击确认。
8. 输入一条人工回复并发送。
9. 上传一个测试附件，例如 PDF 或图片，并发送给客户。
10. 在右侧资料表单填写 WhatsApp、邮箱、公司、国家、客户需求产品等字段。
11. 点击「更新线索」。
12. 进入左侧「线索」菜单，找到刚才这条线索。

预期结果：

- 客户消息能自动进入对话工作台。
- 该会话只出现在销售 A 的 WhatsApp 工作台中，不出现在其他销售个人 WhatsApp 工作台中。
- 点击接管会话前不能人工发送消息；接管确认后可以发送。
- 文本和附件都能发出，附件名称不乱码。
- 点击「更新线索」后，线索表中能看到对应记录。
- 客户来源为 WhatsApp。
- 若填写了 WhatsApp 或邮箱，线索阶段自动变成「有效线索」；未填写时保持当前阶段。
- 右侧表单信息与线索表字段一致。

辅助断言：

- `conv.conversations.external_chat_id` 使用 `<phone>@c.us`。
- 同一手机号不能因 `@lid` / `@c.us` 生成两条会话。
- `conv.contacts.twenty_opportunity_id` 指向新建或更新后的线索。

### E2E-03 销售主动发起 WhatsApp 会话

| 项 | 内容 |
|---|---|
| 操作者 | 销售账号 A |
| 入口 | CRM「对话工作台」→ 新建 WhatsApp 会话 |
| 前置 | 销售 A 已绑定 WhatsApp，目标手机号是真实 WhatsApp 账号 |

操作步骤：

1. 销售 A 打开「对话工作台」。
2. 点击左侧搜索框旁的新建 WhatsApp 会话按钮。
3. 输入带国家区号的目标手机号。
4. 点击「搜索账号」。
5. 确认搜索结果显示该 WhatsApp 账号存在且号码正确。
6. 输入首条消息。
7. 点击下一步或发送，并在二次确认中确认发送。
8. 等待客户回复。
9. 查看会话列表和聊天区。

预期结果：

- 未搜索成功前，首条消息不可发送。
- 搜索失败时显示中文可读原因。
- 发送成功后会话进入人工接管状态。
- 客户回复后，回复必须进入同一个会话框。
- 左侧会话列表不能出现同一手机号两条记录。

辅助断言：

- 真实发送可以使用 WAHA 返回的 provider chatId。
- CRM 落库仍统一使用 `<phone>@c.us`。

### E2E-04 官网客服访客咨询，销售在工作台接管

| 项 | 内容 |
|---|---|
| 操作者 | 官网访客 + 销售账号 A |
| 入口 | 官网 Widget → CRM「对话工作台」 |
| 前置 | 官网 Widget 指向当前环境；AI 服务正常 |

操作步骤：

1. 官网访客打开官网页面，点击悬浮 AI 客服入口。
   - 推荐使用带 UTM 的页面，例如 `?utm_source=test&utm_medium=e2e&utm_campaign=crm_context`。
2. 访客输入一条产品或公司咨询问题。
3. 销售 A 登录 CRM，进入「对话工作台」。
4. 点击顶部「官网」渠道。
5. 找到刚进入的官网访客会话。
6. 打开会话，确认能看到访客消息和 AI 回复。
7. 销售点击「接管会话」，确认人工接管。
8. 销售发送一条人工回复。
9. 销售发送一个附件给官网访客。
10. 在右侧资料表单补充 WhatsApp、邮箱、公司、国家、客户需求产品。
11. 点击「更新线索」。
12. 进入「线索」表查看该线索。

预期结果：

- 官网访客无需登录即可发起会话。
- 官网消息自动进入 CRM 对话工作台。
- 会话详情顶部展示访客地域上下文：国家、地区、城市、时区、IP。
- 如果页面带 UTM，详情顶部展示 UTM、访问页、来源页。
- 新官网会话不能只保存 `172.18.0.x` 作为访客 IP；旧历史记录没有真实 IP 时不要求回填。
- AI 回复和人工回复保存在同一会话历史中。
- 人工接管后 AI 不再继续抢答。
- 官网渠道作为公共入口，全员默认可见；实际负责关系由接管/负责人记录。
- 更新线索成功后，客户来源为「官网客服」。
- 发送附件后，官网 Widget 可看到附件卡片，CRM 时间线也保留附件记录。

### E2E-05 官网表单提交后，销售处理线索

| 项 | 内容 |
|---|---|
| 操作者 | 官网访客 + 销售账号 A |
| 入口 | 官网表单 → CRM「线索」 |
| 前置 | 官网表单 API 已连接当前 CRM |

操作步骤：

1. 官网访客填写表单：姓名、公司、联系方式、国家、感兴趣产品等字段。
2. 提交表单。
3. 销售 A 登录 CRM。
4. 点击左侧「线索」菜单。
5. 在表格中找到刚提交的线索。
6. 打开该线索或直接在表格中查看字段。
7. 销售手动修改线索阶段，例如从「未处理线索」改为「线索」或「有效线索」。
8. 销售填写或确认「客户需求产品」。

预期结果：

- 官网表单首次进入线索时，客户来源为「官网表单」。
- 官网表单首次进入线索时，任务进度为「未处理线索」。
- 后续销售手动修改阶段后，系统不能自动把它重置回「未处理线索」。
- 官网表单重复提交时，应保留提交历史，不覆盖人工推进后的核心阶段。

### E2E-06 线索转客户

| 项 | 内容 |
|---|---|
| 操作者 | 销售账号 A |
| 入口 | CRM「线索」 |
| 前置 | 已有一条线索；线索来自 WhatsApp、官网客服或官网表单均可 |

操作步骤：

1. 销售 A 打开「线索」表。
2. 选择一条测试线索。
3. 如果「客户需求产品」为空，先尝试转客户。
4. 查看失败提示。
5. 填写「客户需求产品」。
6. 再次点击「转客户」。
7. 在二次确认弹窗中确认。
8. 进入「客户」表，查找刚生成或更新的客户记录。

预期结果：

- 未填写「客户需求产品」时，不能转客户。
- 失败原因必须清楚说明需要填写「客户需求产品」，不能乱码、不能重复展示多个提示。
- 填写产品后可成功转客户。
- 若客户已存在，应更新已有客户，不重复创建。
- 客户记录与线索保留同一 `syncGroupCode` 和线索id。

### E2E-07 线索转项目

| 项 | 内容 |
|---|---|
| 操作者 | 销售账号 A |
| 入口 | CRM「线索」 |
| 前置 | 线索已填写「客户需求产品」 |

操作步骤：

1. 销售 A 打开「线索」表。
2. 选择一条测试线索。
3. 点击「转项目」。
4. 在二次确认弹窗中确认。
5. 进入「项目」表。
6. 查找刚生成的项目。
7. 回到原线索，确认关联关系仍存在。

预期结果：

- 一个线索只能转出一个项目；重复点击不能重复创建。
- 项目、客户、线索三者线索id一致，底层关联编码一致。

### E2E-08 三维度字段同步

| 项 | 内容 |
|---|---|
| 操作者 | 销售账号 A |
| 入口 | CRM「线索 / 客户 / 项目」 |
| 前置 | 同一条数据已经完成线索 → 客户 → 项目 |

操作步骤：

1. 在线索中修改一个已映射字段，例如 WhatsApp、邮箱、国家/地区、官网链接、最新跟进、负责人或协办人。
2. 打开客户表，查看对应客户字段。
3. 打开项目表，查看对应项目字段。
4. 再从客户或项目中修改同一类映射字段。
5. 回到另外两个维度检查同步结果。

预期结果：

- 三个维度中已确认映射的字段应保持同步。
- 不参与映射的字段不应被误覆盖。
- 受保护字段底层 id/name/type 不允许被修改。
- 当前受保护字段包括：`youXiang`、`name`、`whatsapp`、`guoJiaDiQu`、`guanWangBeiZhu`。

### E2E-09 负责人转交与沟通状态查看

| 项 | 内容 |
|---|---|
| 操作者 | 销售账号 A、销售账号 B、销售主管/Boss |
| 入口 | CRM「线索 / 客户 / 项目 / 沟通状态 / 对话工作台」 |
| 前置 | A 名下已有一条带聊天记录的线索，且已关联客户/项目 |

操作步骤：

1. A 在线索中把负责人转交给 B，或由有权限账号完成分配。
2. B 登录 CRM，进入线索、客户、项目查看该数据。
3. B 进入对话工作台，重新打开该客户相关会话。
4. 查看右侧表单是否自动带出该客户资料。
5. 销售主管或 Boss 打开「沟通状态」。
6. 点击该客户的沟通记录，查看完整聊天上下文。

预期结果：

- 负责人转交后，B 能看到相关业务数据。
- 对话工作台右侧表单能同步展示已维护的客户资料。
- 历史聊天记录不能丢。
- WhatsApp 工作台仍按个人绑定账号隔离。
- 官网和 email 会话作为公共入口默认全员可见。
- 销售主管/Boss 可在「沟通状态」查看真实聊天内容，但不应在工作台越权操作个人 WhatsApp。

## 2. 技术链路与数据落点（辅助定位）

### 链路 1：官网表单 → 线索 → 转客户 → 转项目

```
官网表单 POST /api/website/form（x-webhook-secret 鉴权）
  └─ normalizeWebsiteFormPayload() 归一化 5 字段
  └─ createOpportunity（GraphQL）
```

### TC-WA-01 入站消息 → 自动落库 + 自动建线索

- **预期**：
  1. 返回 200 `{received:true}`
  2. `conv.contacts`（channel=whatsapp）、`conv.conversations`、`conv.messages`（sender_type=customer）各新增 1 条
  3. 自动建线索：`opportunity.stage = XIANSUO`、`keHuLaiYuan = WHATSAPP`、`conv.contacts.twenty_opportunity_id` 指向该线索

### TC-WA-02 工作台「转为线索」补全 → 更新线索 + stage 升级
- **前置**：TC-WA-01 的会话
- **步骤**：调 `convert-to-lead`，传 `name/company/phone/email/product`
- **预期**：
  1. 返回 200（`updated=true`，因已自动建）
  2. DB：`opportunity.stage` 由 XIANSUO → `YOUXIAO_XIANSUO`（补了电话/邮箱）；`lianXiRenXingMing = name`；`keHuXuQiuChanPin`、`youXiangPrimaryEmail`、`whatsappPrimaryPhoneNumber` 落库

### TC-WA-03 更新线索信息（二次转线索 / 界面改字段）
- **前置**：TC-WA-02 的线索
- **步骤**：再次调 `convert-to-lead` 改字段，或 GraphQL `updateOpportunity` 改电话/邮箱
- **预期**：`opportunity` 字段更新；若走界面改 phone/email，`opportunity-updated` webhook 触发后，已转客户的 Person 电话/邮箱同步（单向）

- **前置**：线索已填产品
- **步骤**：调 `convert-to-person`
- **预期**：同 TC-WF-04（Person 生成、pointOfContactId 回填、leadNo 同源）

### TC-WA-05 转项目
- **前置**：已转客户
- **步骤**：调 `convert-to-project`
- **预期**：同 TC-WF-05（项目生成、三表线索id同源、linkedProjectId 回填）

### TC-WA-06 主动新建会话复用 `@lid/@c.us`
- **前置**：CRM 用户已绑定 WhatsApp，WAHA session 为 `WORKING`；目标外部号码真实注册 WhatsApp。
- **步骤**：
  1. 调 `/api/conversations/whatsapp/check` 搜索目标手机号。
  2. 调 `/api/conversations/whatsapp` 发送首条消息。
  3. 让目标外部号码回复一条消息。
  4. 查询 `conv.contacts`、`conv.conversations`、`conv.messages`。
- **预期**：
  1. 只存在一条 `conv.conversations.channel='whatsapp' AND external_chat_id='<phone>@c.us'`。
  2. 出站消息和入站回复都落在同一个 `conversation_id`。
  3. 若 WAHA 返回 `providerChatId=@lid`，该值只允许出现在发送结果或外部消息 id 中，不应作为 CRM 新会话 `external_chat_id`。
  4. 再次对同一手机号主动发送，应复用已有 `conversation_id`，不新增会话。

### TC-WA-07 WAHA session webhook 自动校准
- **前置**：`conv.channel_accounts` 中至少存在一个有效 WhatsApp 绑定。
- **步骤**：
  1. 重启 middleware。
  2. 等待 1 个巡检周期。
  3. 调 WAHA `/api/sessions/:session` 查看 config。
- **预期**：
  1. session `config.webhooks[0].url = http://middleware:3002/api/whatsapp/webhook`。
  2. events 至少包含 `message`、`message.ack`、`session.status`。
  3. WAHA 新发出的 webhook 返回 200。
  4. 旧队列里如果仍有 `host.docker.internal` 的历史重试日志，不影响本用例通过，但需记录。

### TC-WA-08 WAHA 状态巡检落库
- **前置**：至少存在 1 个 `conv.channel_accounts.status <> 'unbound'` 的 WhatsApp 绑定。
- **步骤**：
  1. 记录该绑定 `metadata.lastWahaStatusAt`。
  2. 等待 60 到 90 秒。
  3. 再次查询同一绑定。
- **预期**：
  1. `metadata.lastWahaStatusAt` 更新。
  2. `metadata.lastWahaStatusSource` 为 `poller`、`webhook` 或 `status-endpoint`。
  3. `status` 与 WAHA 当前 session 状态一致。

### TC-WA-09 掉线状态处理
- **前置**：有测试 session，可安全模拟 `FAILED` / `STOPPED` 或观察真实掉线。
- **步骤**：
  1. 让 session 进入 `FAILED` 或 `STOPPED`，或停止对应 session。
  2. 等待巡检。
  3. 查看 middleware 日志和 `conv.channel_accounts`。
- **预期**：
  1. middleware 尝试调用 restart。
  2. 数据库状态更新为 restart 后的真实状态。
  3. 如果状态是 `SCAN_QR_CODE`，设置页应提示用户重新扫码/配对。
  4. 不得继续把已掉线 session 显示为可用在线状态。

## 7. 权限与沟通状态补充测试

### TC-RBAC-01 普通销售只能看自己的 WhatsApp 会话
- **前置**：销售 A、销售 B 分别绑定不同 WhatsApp session。
- **步骤**：销售 A 登录对话工作台，切到 WhatsApp 渠道。
- **预期**：只看到 A 自己绑定 session 的会话；看不到 B 的 WhatsApp 会话；即使 URL 手动访问 B 的会话消息接口也应返回 403/不可见。

### TC-RBAC-02 管理员 / boss 在 WhatsApp 工作台也不跨个人号
- **前置**：管理员或 boss 没有绑定某销售 WhatsApp session。
- **步骤**：管理员 / boss 打开对话工作台 WhatsApp 渠道。
- **预期**：WhatsApp 仍按个人号隔离；不显示其他销售个人 WhatsApp 会话。

### TC-RBAC-03 销售主管 / boss 在沟通状态可看全部
- **前置**：存在多个销售的官网/WhatsApp/邮件会话，且已生成沟通状态记录。
- **步骤**：销售主管或 boss 打开「沟通状态」对象，点击「查看对话内容」。
- **预期**：可看到全部沟通状态记录；详情弹窗内可查看完整消息文本和附件链接；boss 仍不能发送消息或接管。

### TC-RBAC-04 负责人 / 协办人 / 协办人2 可见性
- **前置**：同一线索关联客户/项目，分别设置负责人、协办人、协办人2。
- **步骤**：对应成员登录对话工作台和沟通状态。
- **预期**：只要成员在三维度任一关联记录上是负责人/协办人/协办人2，即可看到该客户相关会话；无关成员不可见。

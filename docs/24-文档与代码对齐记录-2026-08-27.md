## 1. 核心架构转向：去 syncGroup 镜像 → 客户/公司主数据

**旧模型**：线索 / 客户 / 项目 通过 `syncGroupCode` 做 **1:1:1 字段镜像同步**（触发器把产品、金额、跟进、负责人等跨三表覆盖）。

**问题**：一个客户只能对应一条线索/项目；回访、多项目场景互相覆盖；邮箱防撞导致静默丢字段（空 leadNo / 空邮箱即源于此）；复杂度与 bug 高。

**新模型（标准 CRM 主数据 + 引用）**：

- **客户(person)、公司(company) = 去重主数据**。客户按 邮箱 / 手机号 唯一（邮箱唯一索引保留）。
- 线索、项目通过 `pointOfContact` / `company` 关系**引用**主数据（多对一）。
- 关系基数：**1 客户 : N 线索 : N 项目**；**1 公司 : N 客户 / N 线索 / N 项目**。
- 从客户维度看其名下线索/项目：反向列表 `作为联系人的线索`(pointOfContactForOpportunities) / `客户联系项目`(contactProjects)。

**落地**：

- `migrations/20260827_retire_syncgroup_mirror_triggers.sql`：退役 14 个镜像/分组触发器（`*_sync_shared_fields`、`*_owner_contact_sync`、`*_customer_website_sync`、`*_resolve_sync_group`、`ensure_opportunity_sync_group_code`、`opportunity_website_contact_name_sync`、`dedup_website_form_opportunity`）。只删触发器、保留函数；回滚见 `_ROLLBACK.sql`。
- 保留工具触发器：`opportunity_leadno_default_trg`、`opportunity_website_form_default_stage_before_insert`。
- 不做历史数据迁移（存量上线前清库）。

## 2. 转客户去重（弹窗判断，不自动合并）

`POST /api/opportunities/:id/convert-to-person` 重构：

1. 首次调用（无 `mode`）→ `findDuplicateCustomers()` 按**邮箱/手机号**查客户主数据。
2. **命中重复** → 返回 `409 DUPLICATE_CUSTOMER` + `duplicates`（疑似客户 + 每个客户名下的线索/项目），前端 `openDuplicateModal()` 弹窗展示。
3. 用户选择：
   - **分配给已有客户** → `mode=assign` + `personId`：线索 `pointOfContact` 指向该客户，不新建、不改客户主数据。
   - **仍然新建客户** → `mode=create`：`createPersonFromOpportunity()` 新建；若邮箱已被占用，新客户邮箱留空（避让唯一索引）。
4. **未命中** → 直接新建客户。

- `createPersonFromOpportunity()` 永远新建（不再按邮箱/电话/回访客复用旧客户）。
- `convert-to-project`：线索已有客户则复用，否则新建。
- 真正的「合并两条重复客户/项目」是**未来独立功能**（人工/系统判定同一客户，如同一项目从 WhatsApp 与官网两渠道进来），本期只提示不合并。
- 前端：`nginx/inject/src/60-convert.js` 加 `openDuplicateModal`，`runConvert` 处理 409 后带 `mode` 重发；bundle `?v=20260827-convert-dedup-v1`。

## 5. AI 客服：知识库就绪前「强制全兜底」

**关键机制辨析**（避免再踩坑）：

- `aiEnabled`（含 middleware `conv` 侧的 `ai_enabled`）是**自动回复总开关**。关闭后 `ai_service.reply` 直接返回 `no_reply`（**什么都不发，连兜底都没有**），middleware `requestAiReplyIfAllowed` 也会 `if (!policy.aiEnabled) return` 直接跳过。**「关闭 AI」≠「走兜底」，而是「完全不自动回复、纯等人工」**。
- 回复决策（`ai/service.py reply()`）：`decision.replyMode == 'aiReplying'`（需 `aiEnabled AND aiBackendAvailable`）才继续；随后 **知识检索无命中 → `status=fallback`（离线兜底话术）**；**有命中 → `status=reply`（LLM 真答）**。
- 知识库并非空：ai-service 启动 `seed_default_documents()` 内置 NHD 产品**种子文档**，所以 AI 开着时产品提问会命中种子库、生成真答（曾出现「立式压滤机 HDLY」真答即由此而来）。

**当前生产配置（知识库未正式搭建，要求全部走兜底）**：

| 设置 | 值 | 作用 |
|---|---|---|
| `aiEnabled` | `true` | 自动回复链路开，兜底才会发 |
| `aiBackendAvailable` | `true` | 进入 `aiReplying` 模式 |
| `knowledgeMinScore` | `100` | 种子文档打分达不到 100 → 检索永远无命中 → 全部落 `fallback` |

- 已持久化 sqlite `settings` 表；实测中/英文产品提问均返回 `status=fallback`（`knowledge_not_found`）+ 兜底话术，无真答。
- **知识库正式就绪后**：把 `knowledgeMinScore` 调回 `60`（`POST /api/agent/settings` 或 设置→AI 客服设置），即恢复 LLM 真答。
- **缺省值**：`config.py DEFAULT_SETTINGS` 已改为 `aiEnabled: True` / `aiBackendAvailable: True` / `knowledgeMinScore: 100`，全新部署/重置默认即「强制全兜底」。

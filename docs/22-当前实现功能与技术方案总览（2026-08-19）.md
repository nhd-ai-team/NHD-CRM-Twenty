## 2. 核心技术方案

### 2.1 请求链路

```
浏览器 / 官网 / WhatsApp
  -> Cloudflare Tunnel / crm.chinanhd.com
  -> twenty-portal nginx
     -> Twenty 原生页面与 GraphQL
     -> /conv-api/* 转发到 middleware
     -> /chat/ 转发到 chat-ui
  -> PostgreSQL + Redis
```

### 2.2 三类数据存储

| 数据类型 | 存储位置 | 说明 |
|---|---|---|
| CRM 结构化业务数据 | Twenty workspace schema：`workspace_3zyju8y4v9gnoifvksi4cn23f` | 线索、客户、项目、公司、字段元数据、视图配置 |
| 会话与渠道数据 | `conv` schema | conversations、messages、contacts、channel_accounts、roles、audit、website_form_submissions |
| 附件文件 | middleware 本地上传目录，对外通过 `/conv-api/uploads/conversation-files/*` 访问 | 会话消息只保存附件元数据和 URL |

### 2.3 官网会话来源信息链路

官网访客来源信息不写入 Twenty 客户主表，统一沉淀在 `conv.contacts`，供对话工作台和后续分析使用。

```text
官网 widget
  -> ai-service /api/website-channel/messages
  -> ai-service forward_to_crm()
  -> middleware /api/website/webhook
  -> conv.contacts / conv.messages
  -> chat-ui 对话工作台
```

当前字段口径：

| 字段 | 说明 |
|---|---|
| `ip_address` | 官网访客公网 IP，仅用于审计和 GeoIP 推断 |
| `geo_country_code` / `geo_country_name` | 国家 |
| `geo_region` / `geo_city` | 地区 / 城市 |
| `geo_timezone` | 时区，前端格式化为 UTC 友好显示 |
| `geo_latitude` / `geo_longitude` | 经纬度 |
| `geo_source` | GeoIP 来源，目前默认 `ip-api` |
| `landing_page_url` | 访客发起会话所在页面 |
| `referrer_url` | 来源页 |
| `utm_source` / `utm_medium` / `utm_campaign` / `utm_term` / `utm_content` | UTM 来源参数 |

安全边界：

- `middleware` 只保存公网 IP；私网、回环、容器网段 IP 不入库、不解析。
- 请求体中的 `clientIp` 只在 `/api/website/webhook` 通过内部密钥校验后作为 AI 服务转发兜底使用。
- WhatsApp / email 没有 Web 访问上下文，不展示伪造地址。
- 历史记录若只保存了 `172.18.0.x` 这类容器内网 IP，无法回填真实访客位置。

### 2.4 权限模型

| 场景 | 当前规则 |
|---|---|
| WhatsApp 工作台 | 不管 admin / boss / sales，个人 WhatsApp 会话只看自己绑定账号相关的会话 |
| 官网客服工作台 | open 公共会话可见；接管后按负责人、参与人、线索/客户/项目负责人或协办人可见 |
| 沟通状态 | `allowPrivilegedAllChannels` 场景下管理员 / boss / 销售主管可看全部沟通记录；普通销售仍按本人相关数据看 |
| boss | 仅查看，不允许发送消息、接管、改分配 |
| 协办人 | `xieBanRenId` 和 `xieZuoRen2Id` 纳入会话可见性判断 |
| 公共渠道 | 官网客服和 email 是公共入口，默认全员可见；接管后仍保留参与人/负责人视角用于历史追踪 |

### 2.5 WhatsApp 会话身份归并

WhatsApp Web / WAHA 可能对同一个联系人返回两类 ID：

- 手机号 JID：`8615810780090@c.us`
- LID：`200751838167131@lid`

CRM 内部会话主键口径统一为手机号 JID：

1. 入站 webhook：通过 `resolvePhone()` 把 `@lid` 解析为手机号，最终写入 `external_chat_id = <phone>@c.us`。
2. 主动新建 / 出站发送：搜索号码时 WAHA 返回的 `checked.chatId` 只作为 `providerChatId` 用于真实发送；CRM 落库仍使用 `<phone>@c.us`。
3. 查找已有会话时同时匹配 canonical chatId、provider chatId 和联系人 phone，命中后复用旧会话，不新建重复会话框。

该方案解决「我发消息在一个会话框，对方回复在另一个会话框」的问题。

### 2.6 WhatsApp 在线状态与掉线处理

当前状态来源有三类：

| 来源 | 触发时机 | 写入位置 |
|---|---|---|
| WAHA `session.status` webhook | WAHA 会话状态变化 | `conv.channel_accounts.status` + `metadata.lastWahaStatus*` |
| 设置页状态接口 | 用户进入渠道设置 / 点击刷新状态 | 同上 |
| middleware 后台巡检 | 默认每 60 秒 | 同上 |

处理规则：

- `WORKING`：在线，可发送 / 接收。
- `SCAN_QR_CODE`：需要重新扫码或配对，系统不能自动恢复为在线。
- `FAILED` / `STOPPED`：巡检会自动调用 WAHA restart，再把最新状态写回数据库。
- `NOT_FOUND` / `UNKNOWN`：通常表示 WAHA session 丢失或 WAHA API 异常，需要重新启动服务或重新绑定。

个人 WhatsApp Web 的登录态由 WhatsApp 控制，当前系统只能做到「及时发现、及时展示、能自动 restart 的自动处理」，不能承诺一周内绝不掉线。

## 5. 需要继续稳定测试的点

| 测试项 | 重点 |
|---|---|
| 设置页渠道绑定 | 进入 `/settings/profile#channels` 不应让左侧设置菜单消失；刷新后不会长时间卡死 |

| 权限隔离 | 普通销售只看到自己的 WhatsApp 和自己相关数据；销售主管 / boss 在沟通状态可看全部 |

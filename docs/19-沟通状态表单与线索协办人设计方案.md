## 一、沟通状态表单（全渠道对话历史档案）

### 1.1 定位

「全渠道对话历史档案」，两大用途：
1. **话术审计**：老板/主管回溯各渠道对话，评估销售沟通话术是否合理、有无优化空间。
2. **销售 Agent 数据源**：对话历史作为销售 AI Agent 的上下文来源。

> 结论：必须保留消息全文，不能只留「状态」而丢弃内容。

### 1.2 已确认决策

| 决策点 | 结论 |
|---|---|
| 粒度 | **1 会话 = 1 记录** |
| 状态维度 | **会话状态 + 沟通结果 两个字段并存**（一条记录同时展示两个维度） |
| 聊天内容 | **需要看到具体内容**（方案 C：原生表单 + 气泡钻取） |
| 历史回填 | **只同步新会话，不回填历史** |

### 1.3 字段设计（`duiHuaLiShis`，一记录=一会话）

| 字段 | Twenty 类型 | 用途 / 来源 |
|---|---|---|
| 客户 | 关联 → People | 关联联系人（`conv.contacts.twenty_person_id`） |
| 公司 | 关联 → Company | 有则关联 |
| 线索 | 关联 → Opportunity | `conv.contacts.twenty_opportunity_id` |
| 渠道 | 单选 | 官网客服 / WhatsApp / Instagram / Facebook / 邮件 |
| 会话状态 | 单选 | 进行中 / AI 托管 / 人工接管 / 已关闭（映射 `conv.status`） |
| 沟通结果 | 单选 | 待跟进 / 已回复 / 已转化 / 无效 / 其他（**枚举值待最终确认**，可销售手工改） |
| 负责人 | 关联 → 成员 | `agent_id`/`owner_id`（审计时按销售筛） |
| 最近消息时间 | 日期 | `last_message_at` |
| 最新消息摘要 | 文本 | `last_message_preview` |
| 消息数 | 数字 | 会话消息数 |
| 含人工消息 | 布尔 | 快速筛「有真人跟过的」会话（审计优先看） |
| 会话外部 ID | 文本（隐藏） | 幂等 upsert 键（`conv.conversations.id`） |

### 1.4 视图设计（全用原生）

- **默认表格视图**：按「最近消息时间」倒序；列 = 客户 / 渠道 / 会话状态 / 沟通结果 / 负责人 / 摘要 / 时间。
- **看板视图**：按「会话状态」分列（可切「沟通结果」分列）。
- **保存视图**：`Boss 全量`、`我的会话`、`按渠道`。

### 1.5 内容保留与落点

| 用途 | 落点 |
|---|---|
| 话术审计（人看） | 原生表格/看板概览 → 点进单条 → 「查看对话内容」**内联文本弹窗**读全文（2026-08-19 起，替代原 HistoryApp 跳转，见 docs/21） |
| Agent 数据源（机器读） | 现有 `GET /api/conversations/:id/messages`，Agent 直接复用；表单与 API 指向同一份 `conv.*` 数据 |

### 1.6 同步机制

- 各渠道入站入口（`persistWhatsAppMessage` / 官网客服 / 官网表单 / Instagram 等）会话**创建时** upsert 一条 `duiHuaLiShis`（幂等键 = `conv.conversations.id`）；状态/摘要/消息数/时间等字段在后续消息时增量更新。
- **只同步新会话，不回填历史**（用户已确认）。
- 写入走 GraphQL mutation（或直写 workspace schema 表 + 精准清 Redis 元数据缓存 + 重启 server/worker/portal，沿用 `twenty-crm-field-and-deploy` 技能）。

### 1.7 方案确认

采用 **方案 C（原生表单 + 内容弹窗）**：概览用 Twenty 原生表格/看板、内容用「查看对话内容」内联文本弹窗（2026-08-19 起，不再跳转页面）、Agent 用现有 API，三处复用，几乎不新增自研面。

## 二、线索协办人（主负责人分配协办人）

### 2.1 需求（已确认）

线索分配**主负责人**后，主负责人的账号可给该线索分配**协办人**。协办人获得该线索&客户&项目的**完整权限**：
- 历史信息（线索 / 客户 / 项目三表数据）
- 对话记录（各渠道会话历史）
- 继续沟通的权限（接管、回复、发消息）

> 典型场景：负责人休假，协办人协助跟进——「和这个客户有关的权限都要有」。

### 2.2 库内真实字段（已核实，2026-08-18）

- **主负责人** = `opportunity.owner`（label「负责人」，`RELATION` → `workspaceMember`，对象 id `c122457c-83e9-492f-bf87-4ada38e37f84`）。
- **协办人元数据已部分存在**：`opportunity.xieBanRen`（label「协办人」）、`opportunity.xieZuoRen2`（label「协办人2」），均为 `RELATION` → `workspaceMember`（多对多，各自有反向字段）。
- **但 middleware 里没有任何协办人/owner 可见性逻辑**（grep 仅命中 `conv.conversations.owner_id`，与 opportunity 无关）。→ 现状：字段是空壳，没有权限落地、也没有「仅主负责人可分配」校验。

### 2.3 方案：复用现有字段 + middleware 补权限

**存储**：复用已存在的 `owner`（主负责人）+ `xieBanRen`（协办人）。
- 建议**整合**：把 `xieBanRen` + `xieZuoRen2` 两个散字段收敛为**一个**多对多关系字段（它们本就是多对多，可容纳多人），`xieZuoRen2` 废弃/删除（当前为空壳，无数据迁移成本）。
- 若保留现状（两个字段=最多 2 协办人）也可接受，但更推荐收敛成一个。

**权限层（核心，新增）**：middleware 统一在以下可见性判定里并入「协办人」：
1. **线索可见性**：协办人可看/可写该 opportunity（叠加在「sales 看自己」之上）。
2. **会话可见性**：`conversationVisibilityWhere` 增加「协办人分支」——凡归属该线索的会话，协办人可看、可接管、可回复。
3. **附件汇总**：`GET /api/attachments?subjectType=opportunity` 按协办人放行。
4. **跟进记录**：协办人可看/可写该线索的跟进。

**分配鉴权（新增）**：
- `GET/PUT /api/opportunities/:id/collaborators`。
- 仅「主负责人本人（`owner`）或 `admin`」可增删协办人——middleware 校验，不信任前端传参。

**UI（注入层）**：
- 线索详情页注入「协办人」组件（复用「跟进记录」悬浮入口 + 弹窗模式）：展示协办人列表 + 增删，仅主负责人/admin 可见操作按钮。

### 2.4 关键约束

1. **分配权限**：只有主负责人本人或 admin 能加/删协办人。
2. **可见范围覆盖全链路**：线索 + 客户 + 项目 + 对话记录 + 附件 + 跟进，缺一不可。
3. **与角色叠加**：协办人是「加号」不是「替换」；boss 仍只读。
